# Карта тестирования: Сервис выборок (clients-filtering)

Создана 28.10.2026, обновлена 29.10.2026. Живой документ: https://claude.ai/artifact/51oWHufZQ4gL53bygGM3f3

## Область и обозначения

Карта покрывает сервис выборок clients-filtering: выборки клиентов и компаний, выборки аккаунтов, панель фильтрации, расчёт, карточку, реестр, операции, права и API. Вне области: выборки для маршрутов помощи, рассылок и кандидатов — такие проверки помечены «Вне области». Выборки контактных лиц (реестр «Единый контактный лист») входят — раздел 12; объекты бизнес-логики — раздел 13.

**Приоритет:** P1 — блокирующие сценарии и корректность результата; P2 — основной функционал; P3 — второстепенное и косметика.

**Тип проверки:** UI — через интерфейс; API — через методы БЛ (Postman); БД — проверка состояния в таблицах; НФ — нефункциональная.

**Изученные документы:** Описание, Архитектура интерфейса, Панель фильтрации, Конфигурация набора фильтров, Формат выборок, Алгоритмы и процессы, База данных, Организация кода, Права, Выборки клиентов и компаний, Выборки аккаунтов, Публичное API, Roadmap 2026; реестр «Единый контактный лист» (8 документов); оглавление объектов бизнес-логики сервиса v.26.5100.

## 3. Фильтры

Сервис поддерживает 5 форматов значений и \~130 фильтров в 12 группах; проверяем каждый формат по границам, а каждую группу — на корректность отбора против источника данных.

### 3.1 Форматы значений (сквозные проверки)

| № | Формат | Что проверяем | Приоритет |
| --- | --- | --- | --- |
| 3.1.1 | Булевый (true / false / null) | Все три значения; null = фильтр не влияет на результат | P1 |
| 3.1.2 | Дата: min/max + type | type = period с границами (включительно ли min и max), только min, только max, min > max; динамические периоды today, yesterday, week, month, quarter, halfYear, year — на стыках суток, месяца, года и часового пояса | P1 |
| 3.1.3 | Дата: type + count (например ДР nextDays) | count = 0, 1, N; переход через конец года; 29 февраля; автообновляемая выборка пересчитывает период от новой даты | P1 |
| 3.1.4 | Числовой диапазон min/max | Границы включительно, только одна граница, 0, отрицательные, дробные (сумма, средний чек), очень большие, min > max, нечисловой ввод | P1 |
| 3.1.5 | Списочный ids / names / type | Один и несколько элементов; список из нескольких источников (type, например where@point); элемент удалён или переименован после сохранения выборки (текст берётся из names) | P1 |
| 3.1.6 | Кастомный (например intersectionSegment) | Пересечение IN / NOT IN с другой выборкой и папкой; выборка-источник удалена или ещё считается; выборка ссылается на саму себя | P1 |

## 4. Расчёт выборки (ядро)

Главный риск сервиса — неверный состав выборки при сложной логике И/ИЛИ из-за оптимизации (опорные предикаты и дофильтрация). Ключевой приём: один и тот же фильтр должен давать одинаковый результат при UseEnhancedMerge = true и false.

Схема конвейера расчёта (10 шагов): фильтр → нормализация → предикаты/DNF → статистика → опорный → набор опорного (DWC) → дофильтрация → пересечение И → объединение ИЛИ → prefetch (до 1 000 000). При UseEnhancedMerge = false дофильтрации нет.

Каждый И-блок DNF (мегапредикат) набирается по своему опорному предикату, его ID дофильтровываются остальными; блоки объединяются по ИЛИ.

| № | Проверка | Ожидаемый результат | Приоритет | Тип |
| --- | --- | --- | --- | --- |
| 4.1 | Один фильтр | Состав = эталонная выборка из источника (например, реестр «Клиенты» с тем же фильтром) | P1 | UI |
| 4.2 | Два фильтра по И из одного источника и из разных (продажи + СПП) | Пересечение множеств | P1 | UI |
| 4.3 | Два фильтра по ИЛИ | Объединение без дублей | P1 | UI |
| 4.4 | Вложенная логика: AND(OR(AND(A,B), AND(C,D)), AND(F,G)) | Результат = (F∧G∧A∧B) ∨ (F∧G∧C∧D) | P1 | UI/API |
| 4.5 | Пустое пересечение, один из предикатов вернул 0 | Выборка пустая, расчёт завершён | P1 | UI |
| 4.6 | Нормализация: дублирующиеся условия, пустые группы, группа из одного фильтра | Результат как у эквивалентного упрощённого фильтра | P2 | API |
| 4.7 | Выбор опорного: маленький предикат + большой | В MegapredicateLink IsBearing = true у предиката с меньшим (N / LIMIT) × t | P2 | БД |
| 4.8 | Размер предиката неизвестен (-1), нет статистики HandlerStat (первый запуск у клиента) | Расчёт корректен, статистика появляется после запуска | P2 | БД |
| 4.9 | Общий предикат в нескольких мегапредикатах (правило «3 порядка») | Результат верный; при разнице размеров ≥ 1000× опорным остаётся прежний | P3 | БД |
| 4.10 | Сравнение UseEnhancedMerge true / false на наборе фильтров 4.1–4.4 | Состав идентичен; фича filtering_enhanced_merge включается и выключается | P1 | UI |
| 4.11 | Дофильтрация по @Лицо / SPPId между локальной базой и СПП | Клиент с ИНН/КПП находится в обоих источниках; клиент-физлицо без ИНН — по требованиям | P1 | UI |
| 4.12 | Больше 1 000 000 подходящих | Набор останавливается на 1 000 000, статус снимается, событие уходит | P1 | UI/БД |
| 4.13 | Данные источника меняются во время итераций | Нет дублей и падений (уникальность через ResultDataNEW) | P2 | БД |
| 4.14 | Очистка после набора | ResultDataNEW очищена по задаче, статус в TaskMetaNEW не в «расчёте» (0/1) | P2 | БД |

## 6. Операции над результатом

Каждая операция должна взять ровно тот состав, что видит пользователь в карточке (с учётом удалённых и недоступных клиентов).

| № | Операция | Что проверяем | Приоритет |
| --- | --- | --- | --- |
| 6.1 | Вне области: создание рассылки (SMS / Viber / Email) | Получатели = состав выборки; клиенты без нужного канала связи отсеиваются по требованиям; незавершённый расчёт | P1 |
